ระยะ 90 เมตร

ปัญหาที่เจอ

ช่วงสุดท้ายของการส่งอาหารยังเป็นช่วงที่ระบบปล่อยให้คนสองฝ่ายคุยกันเอง

แอปบอกได้ว่าไรเดอร์กำลังมา แต่ไม่ได้บอกว่าจะเจอกันตรงไหน

เมื่อไรเดอร์เข้าใกล้จุดหมาย แผนที่จะแสดงหมุดปักอยู่ที่ตัวอาคาร ซึ่งไม่พอสำหรับคอนโด ตึกออฟฟิศ หมู่บ้านจัดสรร หรือตลาด ทั้งลูกค้าและไรเดอร์จึงต้องประสานกันเองผ่านโทรศัพท์และแชตเรื่องทางเข้า จุดจอด และตำแหน่งจริงของผู้รับ

ผู้ใช้ได้รับผลกระทบอย่างไร

ลูกค้า

ไรเดอร์
วนหาทางเข้าและจุดจอด ต้องโทรซ้ำหลายรอบ เสียเวลาที่ควรใช้กับรอบถัดไป
แพลตฟอร์ม
เวลาส่งต่อรอบยาวขึ้น อาหารเสียคุณภาพ และเสี่ยงเกิดออร์เดอร์ที่ส่งไม่สำเร็จ

ทำไมถึงเลือกปัญหานี้

เพราะมันไม่ใช่ปัญหาของหน้าจอเดียว แต่เป็นช่องว่างของการประสานงานระหว่างคนสองฝ่ายที่ระบบมองไม่เห็น แก้ด้วยการจัดหน้าจอใหม่อย่างเดียวไม่พอ ต้องแก้ที่โครงสร้างข้อมูลของปลายทาง

ระยะ 78 เมตร

สิ่งที่งานวิจัยบอก

ทบทวนงานวิจัยไทยและต่างประเทศเพื่อตรวจสอบว่าปัญหานี้มีอยู่จริงหรือเป็นแค่ความรู้สึก

Olsson et al. (2023)
ศึกษาประสบการณ์รับของที่บ้าน		 ประสบการณ์การส่งมอบมีหลายมิติพร้อมกัน ทั้งความคิด อารมณ์ พฤติกรรม และร่างกาย ไม่ได้จบที่หน้าจอ
Chamchang et al. (2026)
สำรวจผู้บริโภคไทย 397 คน		 ปริมาณพัสดุที่โตขึ้นในไทยสัมพันธ์กับปัญหาส่งไม่สำเร็จ ยืนยันว่าปัญหานี้มีอยู่ในบริบทไทย
Ritthichai
อาชีวอนามัยไรเดอร์มอเตอร์ไซค์ไทย		 ไรเดอร์ทำงานภายใต้แรงกดดันด้านเวลาและสภาพแวดล้อมทางกายภาพ ทุกนาทีที่เสียไปมีต้นทุน

ข้อจำกัดที่ต้องพูดตรง ๆ

งานวิจัยส่วนใหญ่ที่มีอยู่ศึกษาบริบทพัสดุ และเสนอทางออกเป็นตู้ล็อกเกอร์หรือจุดรับของนอกบ้าน ซึ่งเป็นการแก้ปัญหาด้วยการทำให้ทั้งสองฝ่ายไม่ต้องเจอกัน

แต่อาหารรอไม่ได้ การส่งมอบแบบเจอตัวจึงเป็นเงื่อนไขที่เลี่ยงไม่ได้ในบริการนี้ โจทย์จึงไม่ใช่ทำอย่างไรให้ไม่ต้องเจอกัน แต่คือทำอย่างไรให้การเจอกันคาดเดาได้ — ช่องว่างนี้เองคือที่มาของงานชิ้นนี้

Problem & Insight · ไม่เกิน 5–7 บรรทัด

ช่วงร้อยเมตรสุดท้ายของการส่งอาหารยังเป็นช่วงที่ระบบปล่อยให้ลูกค้ากับไรเดอร์ประสานกันเอง แอปแสดงหมุดที่ตัวอาคาร ซึ่งไม่พอสำหรับคอนโด ตึกออฟฟิศ หรือตลาด

เลือกปัญหานี้เพราะงานวิจัยที่สัมภาษณ์ไรเดอร์ส่งอาหารโดยตรงพบว่าความท้าทายส่วนหนึ่งมาจากฝั่งลูกค้าและจากเครื่องมือที่ใช้ทำงาน และเพราะทางออกที่งานวิจัยเสนอกันส่วนใหญ่คือตู้ล็อกเกอร์ ซึ่งใช้กับอาหารไม่ได้

ลูกค้าต้องเฝ้าหน้าจอและถูกโทรหาตอนไม่สะดวก ไรเดอร์เสียเวลาวนหาทางเข้าและโทรซ้ำ ส่วนแพลตฟอร์มได้เวลาส่งที่ยาวขึ้นและความเสี่ยงที่ออร์เดอร์จะส่งไม่สำเร็จ

Proposed Solution Concept & Idea

เปลี่ยนหน่วยข้อมูลของปลายทางจากที่อยู่ เป็นจุดนัดรับ จากเดิมที่ระบบรู้แค่ว่าอาคาร A ชั้น 1 ให้เปลี่ยนเป็นอาคาร A ทางเข้าฝั่ง B ล็อบบี้ รับที่เคาน์เตอร์

ระบบเสนอจุดนัดรับให้ก่อนจากประวัติการส่งสำเร็จในพิกัดเดียวกัน ลูกค้ายืนยันด้วยปุ่มเดียวโดยไม่ต้องพิมพ์ และแก้ได้จนถึงตอนไรเดอร์มาถึง

พร้อมกันนั้นแตกสถานะกำลังจัดส่งออกเป็นห้าสถานะ คือ ใกล้ถึง ถึงแล้ว กำลังหาจุดนัด รออยู่ และส่งมอบ โดยแต่ละสถานะแสดงเฉพาะสิ่งที่ผู้ใช้ต้องรู้และต้องทำในตอนนั้น

จุดนัดรับเป็นข้อมูลชุดเดียวที่ทั้งลูกค้าและไรเดอร์เห็นตรงกัน เมื่อฝ่ายหนึ่งยืนยัน อีกฝ่ายเห็นทันที ระบบจึงเปลี่ยนจากการส่งข้อความไปมาเป็นการทำงานบนสถานะร่วมกัน

Short UI Design Rationale

จัดลำดับข้อมูลตามสิ่งที่ผู้ใช้ต้องตัดสินใจในสถานะนั้น เวลาอยู่บนสุดและใหญ่ที่สุดเพราะเป็นคำตอบของคำถามว่าควรลงไปตอนไหน จุดนัดรับใช้กรอบสีเพื่อแยกชั้นข้อมูลเพราะเป็นข้อมูลใหม่ที่ผู้ใช้ยังไม่คุ้น

แต่ละสถานะมีปุ่มหลักปุ่มเดียว ตัวเลือกรองถูกลดระดับเป็นข้อความ และตัดแผนที่เต็มจอออกในระยะใกล้ เพราะการเห็นหมุดเคลื่อนที่ไม่ช่วยตัดสินใจ แต่ทำให้ผู้ใช้เฝ้าหน้าจอ

ใช้ฟอนต์ monospace กับตัวเลขเพราะความกว้างเท่ากันทุกหลัก ทำให้ตัวเลขไม่ขยับเวลานับถอยหลัง และใช้สีเหลืองเฉพาะกับข้อมูลตำแหน่งเท่านั้น เพื่อให้ผู้ใช้เรียนรู้ความหมายของสีได้ โดยแยกค่าเหลืองสดสำหรับพื้นออกจากเหลืองเข้มสำหรับตัวอักษร เพื่อให้ผ่านเกณฑ์คอนทราสต์

อธิบายขั้นตอนการออกแบบตั้งแต่ได้รับโจทย์ถึงการส่งงาน

เริ่มจากอ่านโจทย์แล้วตั้งใจไม่รีบเลือกปัญหา ไล่หา friction ในระบบส่งอาหารโดยนับทั้งลูกค้าและไรเดอร์เป็นผู้ใช้ จากนั้นทบทวนงานวิจัยไทยและต่างประเทศเพื่อตรวจว่าปัญหาที่คิดไว้มีหลักฐานรองรับหรือเป็นแค่ความรู้สึก

พบว่างานวิจัยส่วนใหญ่ศึกษาบริบทพัสดุและเสนอตู้ล็อกเกอร์เป็นทางออก ซึ่งใช้กับอาหารไม่ได้ จึงเลือกโฟกัสที่ช่วงร้อยเมตรสุดท้าย และนิยามโอกาสเป็นการเปลี่ยนหน่วยข้อมูลจากที่อยู่เป็นจุดนัดรับ

เขียน user flow ทั้งเส้นทางปกติและเส้นทางที่ไรเดอร์หาไม่เจอ ทำ wireframe เพื่อทดลองลำดับข้อมูลในแต่ละสถานะ แล้วจึงลง UI พร้อมสร้างคอมโพเนนต์ที่รับได้ทุกสถานะ

ขั้นสุดท้ายย้อนกลับมาตรวจว่าทุกการตัดสินใจอธิบายที่มาได้ และตัดสิ่งที่อธิบายไม่ได้ออก

อธิบายความเข้าใจเกี่ยวกับ Component / Design System

Design system คือข้อตกลงร่วมกันของทีมว่าอะไรใช้เมื่อไหร่ ไม่ใช่คลังของหน้าจอสวย ๆ คุณค่าของมันวัดที่ว่าคนที่ไม่ได้ออกแบบหน้านั้นหยิบไปใช้แล้วได้ผลลัพธ์ที่ถูกหรือไม่

ในงานนี้จึงแยกคอมโพเนนต์ตามหน้าที่ ไม่ใช่ตามหน้าจอ การ์ดสถานะหนึ่งตัวรับได้ทั้งห้าสถานะผ่าน property เดียวกัน การเพิ่มสถานะใหม่ในอนาคตจึงไม่ต้องสร้างการ์ดใหม่ และไม่เกิดการ์ดที่หน้าตาคล้ายกันแต่ไม่เหมือนกันกระจายอยู่ในไฟล์

ทุกคอมโพเนนต์ต้องมีสถานะ error และ empty ตั้งแต่แรก เพราะสถานะที่ผิดแผนคือจุดที่ระบบมักพัง และเป็นจุดที่ผู้ใช้ต้องการความชัดเจนมากที่สุด

นอกจากนี้ token ของสีต้องมีความหมาย ไม่ใช่แค่ชื่อสี ในงานนี้สีเหลืองผูกกับข้อมูลตำแหน่งเท่านั้น เมื่อความหมายถูกล็อกไว้ที่ token คนที่มาทำต่อจะใช้ผิดได้ยากขึ้น

คุณชอบทำงานร่วมกับทีมในลักษณะไหนมากที่สุด และเพราะอะไร

ชอบทีมที่มีวัฒนธรรม “Design is a shared responsibility” และเปิดกว้างทางความคิด (Psychological Safety) ทุกคนไม่ว่าจะเป็น PM, Dev หรือ Designer สามารถออกไอเดียและท้าทายกันด้วยเหตุผลได้ โดยไม่มี Ego

เหตุผลหลักคือ งานออกแบบที่ดีและใช้งานได้จริง (Feasibility) ไม่สามารถเกิดขึ้นจาก Designer คนเดียวได้ การดึง PM เข้ามาคุยเรื่อง Business Goal ตั้งแต่วันแรก และดึง Dev เข้ามาร่วมรีวิวความเป็นไปได้ทางเทคนิคตั้งแต่เนิ่น ๆ จะช่วยลดปัญหา Redesign หน้างานและทำให้ Launch ได้ตามเป้าหมาย

นอกจากนี้ ยังชอบทีมที่เปิดรับการนำ AI Tools เข้ามาใน Workflow เพื่อช่วยลดขั้นตอน Manual เช่น การ Brainstorm ไอเดียเบื้องต้น, Research ข้อมูล หรือ Generate ตัวอย่าง Prototype/Content ช่วยประหยัดเวลาและพลังงาน ให้ทีมได้โฟกัสกับปัญหาที่สำคัญ การตัดสินใจเรื่อง Experience ที่ซับซ้อน และการสร้าง Value สูงสุดให้กับผู้ใช้งาน
